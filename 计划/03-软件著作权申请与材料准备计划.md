# 《暴躁打包员》软件著作权申请与材料准备计划

> 本文既是开发者执行清单，也是后续 AI 处理软著相关工作的唯一基准。  
> 项目：暴躁打包员（RagingPacker）  
> 首发模式：个人主体、免费下载、仅广告变现、不开放充值或付费内购  
> 目标平台：微信小游戏、抖音小游戏  
> 引擎：Cocos Creator 3.8.8

## 1. 目标与边界

本计划的目标是在不打断正式版开发的前提下，持续积累可用于计算机软件著作权登记、微信小游戏审核和抖音小游戏备案的材料，最终形成一套名称统一、内容真实、可追溯、可补正的提交包。

本项目首发采用纯广告变现（IAA），不提供人民币购买金币、皮肤、体力、礼包、去广告服务或订阅。当前按“无版号小游戏”路线准备软著和平台备案；如未来增加任何付费内购，必须重新评估版号、运营主体和平台支付资质，不得直接沿用本计划作出“无需版号”的结论。

软著证明软件权属，不等同于游戏版号，也不代替微信、抖音要求的小游戏备案、ICP 核准、隐私合规和平台审核。

## 2. 登记信息基准

除非开发者明确书面修改，所有代码页眉、说明书、截图、申请表和平台资料都使用以下信息：

| 字段 | 固定值/填写规则 |
|---|---|
| 软件全称 | 暴躁打包员游戏软件 |
| 软件简称 | 暴躁打包员 |
| 版本号 | V1.0 |
| 内部英文名 | RagingPacker，仅用于仓库、工程和代码，不替代中文登记名称 |
| 软件分类 | 游戏软件/应用软件，按申请系统当时可选分类填写 |
| 开发方式 | 独立开发 |
| 权利取得方式 | 原始取得 |
| 权利范围 | 全部权利 |
| 著作权人 | 开发者本人真实姓名，提交时由本人填写，不在公开仓库保存 |
| 运行平台 | 微信小游戏、抖音小游戏；必要时说明基于 Cocos Creator 3.8.8 |
| 游戏展示名称 | 暴躁打包员 |
| 副标题 | 这个包裹到底能不能发？仅用于宣传，不作为软件名称的一部分 |

一致性是最高优先级：`暴躁打包员游戏软件`、`暴躁打包员`、`V1.0` 的字形、大小写和版本格式不得在材料之间变化。平台要求名称与软著对应时，优先使用软著简称“暴躁打包员”。

## 3. 申请时机

不等到所有运营内容完成才开始整理，但在以下条件全部满足后再形成正式申请材料：

- 核心流程“订单 → 选品 → 包装/标签 → 封箱判定 → 结算”可完整运行。
- 首页、游戏页、结算页和设置/说明入口已有稳定版本。
- 代码已从原型向正式结构演进，主要系统具备真实实现，不使用为凑页数而复制的无效代码。
- 游戏名称、版本号、著作权人和开发完成日期已经确认。
- 至少完成一次 Web 预览和一次目标小游戏平台开发工具验证。
- 申请材料中的功能均已在申请版本中真实存在。

建议在正式版开发中期开始生成草稿，在“双平台首个可运行测试版”完成后冻结 V1.0 申请快照并提交登记。软著申请期间可以继续开发，但必须保留申请快照对应的 Git 标签和提交记录。

## 4. 材料目录规划

后续 AI 创建材料时使用以下目录，不得把身份证、手机号、住址、签名、账号凭证等个人信息写进公开仓库：

```text
软著材料/
├─ README.md                         材料状态、申请入口和人工操作提示
├─ 01-登记信息表.md                  非敏感字段及待本人填写项
├─ 02-软件说明书.md                  可维护的说明书源文件
├─ 03-功能与截图清单.md              截图编号、页面、功能对应关系
├─ 04-源代码交存清单.md              文件顺序、行数、排除项、提交快照
├─ 05-一致性检查表.md                名称、版本、日期、主体检查
├─ screenshots/                     无账号和隐私数据的原始截图
├─ source-export/                   自动生成的代码交存稿，不手工改业务代码
├─ deliverables/                    最终 PDF/DOCX 等非敏感交付件
└─ 私密资料/                         身份证、签字件、申请回执等；已被 Git 忽略
```

`私密资料/` 只能保存在开发者确认安全的位置。AI 不得读取、上传、转述或提交其中内容，除非开发者针对某一次具体操作明确授权。

## 5. 分阶段执行计划

### 阶段 A：从现在开始持续留档

每次完成重要功能或正式界面后：

1. 保持源代码、Cocos `.meta` 文件和配置文件正常提交 Git。
2. 在提交说明中写清功能变化，避免只有“update”等无意义提交。
3. 对首页、订单、传送带、装箱、包装标签、结果和结算页面各保留一张无调试面板的竖屏截图。
4. 第三方素材、字体、音乐和 AI 生成美术记录来源、授权或生成日期。
5. 不把 Cocos 的 `library/`、`temp/`、`build/`、`profiles/` 当作源代码证据。

完成标准：可以从 Git 历史证明 V1.0 的开发过程，关键功能有代码、有界面、有说明。

### 阶段 B：首个正式可玩版本后建立材料草稿

后续 AI 应创建“软著材料”目录，并完成：

- 登记信息表草稿。
- 《暴躁打包员游戏软件 V1.0 使用说明书》草稿。
- 功能模块与源码文件对应表。
- 12～20 张候选截图及截图说明。
- 原创代码行数统计和第三方/生成代码排除报告。
- 名称、版本、日期、主体的一致性检查。

说明书至少覆盖：软件概述、运行环境、启动方式、首页、订单系统、传送带选品、纸箱容量、包装与标签、封箱判定、金币与升级、广告奖励、设置、异常情况和退出方式。

完成标准：即使尚未排版，也已经能确认材料内容全部对应真实功能。

### 阶段 C：冻结 V1.0 申请快照

选择一个稳定提交作为申请基线，并执行：

1. 确认工作区无意外改动并运行自动测试。
2. 使用 Cocos Creator 3.8.8 完成可运行构建和人工流程测试。
3. 记录 Git 提交哈希。
4. 创建 Git 标签，建议为 `copyright-v1.0`。
5. 记录开发完成日期和首次发表状态，由开发者本人确认。
6. 冻结用于申请的源代码、说明书和截图；后续修改不得悄悄替换冻结材料。

开发完成日期必须是真实日期，不能由 AI 猜测。是否发表、首次发表日期和首次发表地点也必须由开发者本人确认。

### 阶段 D：生成源程序鉴别材料

依据现行《计算机软件著作权登记办法》，一般交存规则为：源程序前、后各连续 30 页；不足 60 页则提交全部源程序；除特定情况外程序每页不少于 50 行。

后续 AI 生成代码材料时必须遵守：

- 仅使用申请快照中的开发者原创业务代码和必要配置读取代码。
- 优先选择 `assets/scripts/` 下的 TypeScript 源文件。
- 排除 Cocos 引擎源码、声明文件、依赖包、构建产物、缓存、测试报告、压缩代码和第三方 SDK。
- 文件之间可以加清晰的文件路径分隔注释，但不得重复、伪造或故意扩写代码凑页数。
- 保持代码连续性；前 30 页和后 30 页分别连续，不随意跳行拼接。
- 页眉统一标注“暴躁打包员游戏软件 V1.0”，右上角连续页码。
- 每页代码格式、字号、行距和行数保持一致；最后一页可以少于规定行数。
- 导出前检查代码中不存在密钥、AppSecret、身份证、手机号、真实服务器口令或私人路径。
- 输出“源文件顺序清单”和 SHA-256 校验值，确保可追溯到冻结提交。

当前原型原创 TypeScript 代码量较少。如申请时仍不足 60 页，应提交全部真实源代码，不得制造重复代码；随着正式版架构开发自然增加代码量后再重新统计。

### 阶段 E：生成软件文档鉴别材料

文档采用《暴躁打包员游戏软件 V1.0 使用说明书》。依据现行规则，文档一般提交前、后各连续 30 页；不足 60 页则提交全部文档；除含图片等特殊页面外，文档每页通常不少于 30 行。

说明书编写规则：

- A4 纵向排版，页眉统一写软件全称和版本号，右上角连续页码。
- 截图使用申请快照真实画面，不使用概念图冒充成品界面。
- 截图不得显示调试统计、浏览器地址栏、个人账号、聊天通知或无关桌面内容。
- 每个主要页面都说明进入方式、操作步骤、输入和结果。
- 文档中的按钮名、金币名、页面名必须与游戏实际文字一致。
- 广告章节明确广告是可选激励或结算后的受控展示，不描述任何充值和付费购买。
- 不写尚未实现的排行榜、公会、多人、充值、钻石等功能。
- 最终输出可编辑源文件和 PDF，并进行逐页视觉检查。

### 阶段 F：申请前人工确认与提交

以下内容只能由开发者本人最终确认：

- 真实姓名、身份证明和联系方式。
- 开发完成日期、发表状态及发表日期。
- 是否存在共同开发、委托开发、职务开发或权利争议。
- 所有第三方字体、音乐、图片、SDK 和 AI 美术是否具备合法使用条件。
- 在线申请系统当时展示的字段、材料格式、费用和办理方式。
- 申请确认签章页的签字及最终提交。

AI 可以整理、校验和生成非敏感材料，但不得代签、虚构个人信息、猜测日期或在未经授权时登录并提交政府/版权登记系统。

### 阶段 G：获证后归档与平台使用

获得登记证书后：

1. 核对软件全称、简称、版本号和著作权人。
2. 在私密目录保存证书原件和完整申请回执。
3. 在公开材料中只记录登记号、登记日期和状态；是否公开证书扫描件由开发者决定。
4. 向微信、抖音上传时，保证平台主体与著作权人一致；如不一致，按平台最新要求准备授权材料。
5. 保留平台上传截图、审核结果和补正记录。
6. 后续重大版本另行评估是否登记 V2.0，不修改 V1.0 冻结材料。

## 6. AI 执行协议

以后任何 AI 被要求“准备软著”“生成软著材料”或“检查软著进度”时，应按以下顺序工作：

1. 完整阅读本计划、项目技术计划和当前 Git 状态。
2. 检查是否已达到相应阶段的进入条件，不越阶段伪造材料。
3. 先核对官方最新规则和微信、抖音后台要求；发生变化时提出计划修订，不静默沿用旧规则。
4. 读取真实代码和真实运行界面，只描述已经实现的功能。
5. 将所有待开发者决定的字段标记为 `【待本人确认】`，不得自行填充。
6. 先生成可审阅草稿，再生成最终 PDF/DOCX；最终文档必须逐页检查。
7. 任何个人信息、账号凭证和签字件均不得提交 Git。
8. 每次完成工作后更新“软著材料/README.md”的状态、日期、基线提交和下一步。
9. 未经开发者明确要求，不代为向任何外部系统提交申请或发送材料。

## 7. 验收清单

正式提交前逐项打勾：

- [ ] 软件全称、简称、版本号在所有材料中完全一致。
- [ ] 著作权人与小游戏平台主体一致，或已准备合规授权。
- [ ] 开发方式、权利取得方式和权利范围填写真实。
- [ ] 开发完成日期、发表状态由本人确认。
- [ ] 源代码来自固定 Git 提交并已记录提交哈希。
- [ ] 源代码连续、页码连续、行数和页眉符合当时规则。
- [ ] 已排除引擎、第三方依赖、构建产物和敏感信息。
- [ ] 说明书只描述真实功能，页面名称与游戏一致。
- [ ] 截图清晰，无调试层、个人信息、侵权商标或未授权 IP。
- [ ] 申请表、代码、说明书、截图中的日期不存在矛盾。
- [ ] 已运行自动测试并完整试玩申请快照。
- [ ] 已核对中国版权保护中心及目标平台的最新要求。
- [ ] 身份证、签字件、回执等私密资料未进入 Git。
- [ ] 已备份最终提交包和登记受理信息。

## 8. 当前项目状态与下一步

截至本计划建立时：

- 已具备可玩的 Cocos Creator 3.8.8 原型。
- 已实现主要订单、选品、包装标签、判定、金币、连击、投诉和结算流程。
- 原创 TypeScript 主要集中在 `GameModel.ts` 和 `GameRoot.ts`，约 535 行，尚处于原型结构。
- 尚未建立正式的软著材料目录，也未冻结申请版本。

近期任务：

1. 按技术计划完成正式架构拆分和核心功能闭环。
2. 从现在开始保留规范 Git 历史和无调试层截图。
3. 正式首页、游戏页和结算页稳定后进入阶段 B。
4. 双平台首个可运行测试版完成后冻结 V1.0 申请快照。
5. 由 AI 按本计划生成说明书、代码交存稿和一致性检查表，开发者本人确认后申请。
