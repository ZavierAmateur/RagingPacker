# 《暴躁打包员》项目与技术开发计划

> 英文名：RagingPacker  
> 副标题：这个包裹到底能不能发？  
> 目标平台：微信小游戏、抖音小游戏  
> 引擎：Cocos Creator 3.8.8  
> 团队规模：1 人开发，美术资源由 AI 辅助生成

## 1. 产品目标

将现有可玩 MVP 扩展为可以提交微信、抖音审核并持续更新的正式休闲小游戏。核心体验保持为：

1. 快速读取订单。
2. 从混乱传送带中辨认商品。
3. 选择纸箱、保护包装与配送标签。
4. 承担错装、漏装、超时和错误包装的结果。
5. 用赚取的金币持续改善仓库，并解锁新的区域和搞笑内容。

正式首发版不追求大而全，重点是前 10 分钟好懂、前 30 分钟有变化、连续玩 7 天仍有目标。

## 2. 金币的用途与经济闭环

当前金币只有产出没有消耗，正式版必须形成以下循环：

`完成订单 → 获得金币 → 购买升级/道具/外观 → 挑战更难仓库 → 获得更多金币`

### 2.1 永久功能升级

每项 5 级，价格逐级上升。升级提供便利，但不能自动替玩家完成订单。

| 升级 | 效果 | 建议价格（1～5 级） |
|---|---|---|
| 传送带调速器 | 基础速度降低 3%～12% | 800 / 1,800 / 3,800 / 7,000 / 12,000 |
| 高清订单屏 | 订单显示时间或字体可读性提升 | 600 / 1,500 / 3,200 / 6,000 / 10,000 |
| 智能扫描枪 | 每局 1～3 次短暂标亮正确商品 | 1,000 / 2,200 / 4,500 / 8,000 / 14,000 |
| 自动封箱机 | 缩短封箱动画，不缩短玩家决策时间 | 500 / 1,200 / 2,600 / 5,000 / 9,000 |
| 售后保险柜 | 每个工作日首次轻度错误降低损失 | 1,200 / 2,800 / 5,500 / 10,000 / 16,000 |

不建议直接永久增加纸箱容量，否则会破坏箱型选择。可以把“容量提高”改成可视化更清楚或仅用于特殊活动。

### 2.2 开局消耗道具

每个工作日只能带一种，形成稳定的小额金币回收。

| 道具 | 效果 | 建议价格 |
|---|---|---|
| 冷静喷雾 | 本局前 3 单传送带减速 | 300 |
| 防错印章 | 抵消一次错装投诉，但订单仍失败 | 500 |
| 订单回看券 | 神秘订单可额外查看一次 | 350 |
| 仓库手电 | 停电事件中仍能看见商品颜色 | 450 |
| 加班咖啡 | 一单倒计时增加 6 秒 | 250 |

### 2.3 外观与收藏

- 胶带颜色：1,000～3,000 金币。
- 纸箱皮肤：2,000～6,000 金币。
- 员工服装：4,000～12,000 金币。
- 货车皮肤：6,000～15,000 金币。
- 仓库主题：15,000～30,000 金币。
- 稀有买家评价图鉴：通过正常或特殊组合触发，不直接购买。

### 2.4 经济规则

- 首发只使用金币一种游戏货币，不增加钻石。
- 认真通关永远比故意错装收益高。
- 激励广告只能加速获得资源，不能成为唯一通关方式。
- 每 5 关检查一次金币产销比，目标是普通玩家每 2～3 个工作日能完成一次有效购买。
- 记录 `coin_earned`、`coin_spent`、购买项目和购买后留存，用数据调整价格。

## 3. 正式首发版范围

### 必须完成

- 20～30 种首发商品，具有清晰但存在陷阱的视觉差异。
- 30～50 个数据驱动订单。
- 10 个主线关卡和每日挑战。
- 3 种纸箱、至少 5 种保护包装、6 种配送标签。
- 停电、传送带故障、暴雨、宠物乱入 4 种事件。
- 角色“暴躁值”表现：表情、台词、动作和结算反馈。
- 金币商店、永久升级、开局道具和外观购买。
- 本地存档、音效、音乐、振动开关、新手引导、暂停和重开。
- 微信、抖音小游戏构建与 Android/iOS 真机验证。
- 激励视频广告、插屏广告频控、隐私与合规页面。
- 基础数据埋点和异常日志。

### 首发暂缓

- 公会、多人实时玩法和复杂社交系统。
- 强制排行榜竞争。
- 自建账号系统和重型服务器。
- 复杂剧情、自由装修和角色抽卡。
- 多种付费货币及复杂内购商城。

## 4. 单人开发里程碑（建议 14 周）

| 阶段 | 周期 | 主要工作 | 完成标准 |
|---|---:|---|---|
| P0 预制作 | 第 1 周 | 锁定玩法、经济、美术风格、平台账号与风险 | 两份计划冻结，任务清单可执行 |
| P1 工程重构 | 第 2～3 周 | 拆分现有单体脚本、数据配置化、场景流转、存档 | 核心逻辑可测试，旧功能无回归 |
| P2 正式核心 | 第 4～6 周 | 金币商店、升级、道具、暴躁值、每日挑战、事件扩展 | 30 分钟完整体验闭环 |
| P3 内容与美术 | 第 7～9 周 | 正式 UI、角色、商品、动画、音效、关卡内容 | 原型资源基本全部替换 |
| P4 平台接入 | 第 10～11 周 | 微信/抖音适配、广告、存档、分包、隐私 | 两个平台开发工具可运行 |
| P5 QA 与优化 | 第 12～13 周 | 真机矩阵、性能、断网、前后台、弱网、埋点 | 无阻断问题，指标达到预算 |
| P6 提审准备 | 第 14 周 | 商店素材、录屏、文案、版本号、审核自查 | 可分别上传微信与抖音测试版 |

预留 2 周机动时间处理平台审核和真机兼容问题。不要把审核通过日期绑定到固定宣传日。

## 5. 技术架构改造

现有 `GameRoot.ts` 适合原型，但正式版应拆分职责：

```text
assets/
├─ scenes/          Boot、Home、Game、Result
├─ scripts/
│  ├─ core/         GameFlow、EventBus、Timer、Pool
│  ├─ gameplay/     Order、Conveyor、Packing、Judge、Combo
│  ├─ economy/      Wallet、Shop、Upgrade、Inventory
│  ├─ platform/     PlatformService、WechatService、DouyinService、WebService
│  ├─ save/         SaveData、Migration、StorageService
│  ├─ ui/           Screen、Popup、HUD、Toast
│  └─ config/       配置读取与校验
├─ configs/         items、orders、levels、economy、events JSON
├─ prefabs/         商品、按钮、弹窗、特效
├─ art/
├─ audio/
└─ bundles/         非首屏关卡与主题资源
```

### 核心原则

- 订单、商品、关卡、价格全部配置化，不把内容继续写死在主脚本中。
- 判定逻辑保持为纯函数，继续用 Node 测试。
- 传送带商品使用节点池，禁止持续创建和销毁节点。
- 微信与抖音 API 只能通过 `PlatformService` 调用，玩法代码不得直接引用 `wx` 或 `tt`。
- 存档包含版本号，并提供数据迁移函数。
- 使用事件总线解耦金币、任务、成就、UI 和埋点。

## 6. 平台适配方案

### 微信小游戏

- 使用 Cocos Creator 的微信小游戏构建目标，配置 Portrait 和正式 AppID。
- 构建产物包含 `game.json` 与 `project.config.json`，使用微信开发者工具和真机预览验证。
- 主包预算控制在 4MB 内；非首屏美术按仓库主题拆成 Asset Bundle 分包。
- 首发不做好友排行榜，可在稳定版本后再评估开放数据域。
- 参考：[Cocos Creator 3.8 发布到微信小游戏](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/publish-wechatgame.html)

### 抖音小游戏

- 使用 Cocos/普通小游戏构建产物，在抖音开发者工具导入、真机预览和上传测试版本。
- 抖音普通小游戏整体包默认不超过 20MB，主包不超过 4MB；项目按 4MB 主包预算设计。
- Cocos Creator 3.8.8 满足抖音引擎插件文档所列 3.8.7 及以上版本要求，可在真机验证稳定后启用以降低引擎代码体积。
- 接入平台要求的必接能力，并将侧边栏复访列入提审检查项。
- 参考：[抖音小游戏开发流程](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/minigame/develop)、[抖音代码包与分包限制](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/develop/guide/basic-function/subpackages/introduction)、[抖音游戏引擎插件](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/develop/guide/basic-function/game-plugin/game-engine-plugin)

### 双平台接口

```ts
interface PlatformService {
  getPlatform(): 'web' | 'wechat' | 'douyin';
  saveLocal(key: string, value: string): void;
  loadLocal(key: string): string | null;
  showRewardedAd(placement: string): Promise<'completed' | 'skipped' | 'failed'>;
  showInterstitial(placement: string): Promise<boolean>;
  vibrate(type: 'light' | 'medium' | 'heavy'): void;
  share(payload: SharePayload): Promise<boolean>;
  report(event: string, data: Record<string, unknown>): void;
}
```

## 7. 广告与商业化

- 激励视频：失败后减少一次投诉、神秘订单回看、结算金币加成、临时减速。
- 插屏：只在完整工作日结算后展示，设置频控，不在订单中断操作。
- 首发不接 Banner，避免遮挡竖屏操作区。
- 广告失败、无填充和用户跳过都必须有正常返回路径。
- 所有奖励由广告完整播放回调发放，避免重复领奖。
- 抖音广告结算规则会调整，上线前重新核对官方最新规则：[抖音小游戏广告收入结算规则](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/guide/business-guide/revenue/sharingclause/mini-game)

## 8. 存档设计

```ts
interface SaveDataV1 {
  version: 1;
  coins: number;
  unlockedLevel: number;
  upgrades: Record<string, number>;
  inventory: Record<string, number>;
  ownedCosmetics: string[];
  equippedCosmetics: Record<string, string>;
  reviewCollection: string[];
  settings: { music: boolean; sound: boolean; vibration: boolean };
  daily: { date: string; attempts: number; bestScore: number };
}
```

- 每次订单结算后保存关键进度。
- 写入时增加校验与默认值，损坏数据不得阻止启动。
- 首发以平台本地存储为主；云存档作为上线后迭代，避免扩大首发后端范围。

## 9. 性能和包体预算

- 设计分辨率：750 × 1334，适配安全区与异形屏。
- 目标：主流中端机稳定 60 FPS，低端机不低于 30 FPS。
- 常态 Draw Call 目标低于 50。
- 同屏传送带商品节点建议不超过 10 个，并使用对象池。
- 图集优先使用 1024 或 2048，避免大量散图。
- 主包目标小于 3.5MB，给平台配置和迭代留余量。
- 全包目标小于 15MB，低于抖音默认 20MB 上限并为更新留空间。
- 音频使用短 OGG/MP3，背景音乐循环文件控制在合理体积。
- 进入后台暂停计时和音频，恢复前台时校正状态。

## 10. 测试计划

### 自动测试

- 商品数量、容量、包装、标签和箱型判定。
- 金币产出、购买、余额不足和重复购买。
- 升级效果上下限。
- 存档序列化、损坏恢复和版本迁移。
- 广告完成、跳过、失败和重复回调。
- 关卡完成、三次投诉、超时取消和连击清零。

### 真机测试

- 微信 Android / iOS；抖音 Android / iOS。
- 低内存设备、弱网、断网、来电切后台、锁屏恢复。
- 不同比例屏幕和系统字体缩放。
- 首次启动、二次启动、清缓存、更新覆盖安装。
- 广告无填充和网络中断。

## 11. 数据指标

首发测试阶段重点关注：

- 新手引导完成率。
- 第一关、第三关、第五关完成率。
- 单局平均时长和每日工作日完成数。
- 错误类型分布：错装、漏装、包装、标签、超时。
- 金币产出/消耗比和首次购买时间。
- 激励广告主动观看率、跳过率和失败率。
- 次日留存与 7 日留存。
- 崩溃率、启动耗时和低帧率设备比例。

## 12. 下一步任务顺序

1. 冻结正式版经济和首发范围。
2. 将 `GameRoot.ts` 拆为正式架构。
3. 建立配置表和资源命名规范。
4. 完成 Home、Shop、Upgrade、Game、Result 场景流转。
5. 实现金币消费、存档和平台抽象层。
6. 同步生产第一批正式美术，先替换角色、主界面和 20 种商品。
7. 第 6 周做一次完整 30 分钟内部试玩，决定是否调整范围。
8. 第 10 周开始双平台真机测试，不把平台工作拖到最后。
